## 1. 公开源长什么样

公开星历走 HTTPS，不需要 Space-Track 帐号：

| 用途 | URL |
|---|---|
| 清单 | `https://api.starlink.com/public-files/ephemerides/MANIFEST.txt` |
| ITC / MEME | 同一目录下，清单里的 `MEME_…txt` 文件名 |
| OCM | `https://api.starlink.com/public-files/ephemerides/STARLINK-<norad>.txt` |

`api.starlink.com` 与 `starlink.com` 的同一路径指向 **同一个 GCS 对象**（响应带 GCS 头）。把主机名从其中一个换成另一个，不会从根上解决生产环境的慢。`www.starlink.com` 会 302 到非 www，不要用 www 做基准地址。

当前实现固定使用 `https://api.starlink.com/public-files/ephemerides`。

一份典型 OCM 在存储里是**未压缩正文**，大约 **5.0 MB**（实测如 `STARLINK-1477` 为 5,025,742 字节；2026-11-10 抽到的三份也约 5.02 MB）。清单正文大约 826 KB。

---

## 2. 压缩：必须用内容编码，不要改 URL

GCS 上的对象本身是明文。正确的压缩方式是请求头：

```http
Accept-Encoding: gzip
```

服务端用 **Content-Encoding: gzip** 把正文压后再传送。典型 OCM 的 gzip 传输体大约 **1.91 MB**（`STARLINK-1477` 实测 1,911,640 字节），大约是原文的 38%。清单 gzip 后大约 78 KB。

务必遵守：

1. **只加请求头，不要把 URL 改成 `.gz`。** 公开路径没有提供单独的 `.gz` 文件名作为稳定下载入口；正确姿势是对现有 `.txt` URL 声明 `Accept-Encoding: gzip`。
2. **总传输量按压缩后的约 1.9 MB 计**，不要先拿 5 MB 明文再谈加速。
3. User-Agent 使用 `openspace-safety-api/2.0` 即可。把慢归因于「必须用浏览器 UA，否则返回 HTML」在 2026-11-10 的复查中**不成立**；HTML 防护应放在解压之后做文件头检查，而不是靠伪造浏览器 UA。

压缩解决的是「传多少字节」。生产上更突出的问题是「这些字节走一条 TCP 有多慢」，所以还要做下一节的分段。

---

## 3. 慢在哪：不是源站「本来就很慢」

2026-11-10 在生产服务器（阿里云北京 `123.57.41.32`）上，旧实现（每文件一条 gzip 连接、多文件并行）拉取 3 个 OCM：

- 当日上午一次真实入库拉取：约 **76 秒**（11:46:25–11:47:41 北京时间），大约每文件 25 秒；
- 当日下午对照测试：墙钟 **140.9 秒**，单文件 94～141 秒（约 19～25 KB/s 量级）。

同一批文件在国际出口较好的环境里，单文件常在数秒到十几秒。说明瓶颈主要是 **北京到 GCS 的单连接路径质量**（高时延、单连接限速或易波动），而不是源站生成文件慢，也不是主机名选错。

旧代码已经用 3～4 路**文件级**并发。当一次只拉 3 个文件时，文件级并发已经打满，墙钟取决于**最慢那一条单连接**。要再加快，必须在**同一个文件内部**再拆出多条 TCP。

---

## 4. 方法：对 gzip 传输体做 Range，拼完再解压

核心步骤：

1. 带 `Accept-Encoding: gzip` 发探测请求 `Range: bytes=0-0`，期望 **206**。
2. 从 `Content-Range` 读出**压缩后**对象的总长度（例如 `bytes 0-0/1911640`）。注意：此时的长度是 gzip 传输体长度，不是 5 MB 原文。
3. 若总长达到阈值（实现里为 256 KB），把压缩体均分成 **8** 段（过短的文件按 128 KB 估算段数，至少 2 段）。
4. 8 段并行 GET，每段都带 `Accept-Encoding: gzip` 和对应的 `Range`。
5. 按偏移拼接这 8 段的**原始响应字节**，得到一份完整的 gzip 流（应以 `1f 8b` 开头），再用 `zlib.gunzip` 解出原文。
6. 解压后若文件头像 HTML，视为失败，不要当星历入库。

这是已经被实测验证的行为：

- 带 gzip 的 Range 中，`Content-Range` 的分母是 **gzip 后的大小**；
- 第一段以 gzip 魔数开头，后续段是压缩流的中间字节，单独拿出来解压会失败，必须先拼接；
- 8 段拼起来再解压，与一次完整 gzip GET 再解压的字节**完全一致**。

### 4.1 为什么必须用原始 `https`，不能用 `fetch`

Node 的全局 `fetch`（undici）会按 `Content-Encoding` **自动解压每一段**。分段一旦被提前解压：

- 第一段变成残缺明文，后面几段解压直接失败或得到乱数据；
- 即使勉强拼上，也不是合法原文。

因此 `starlinkDownload.ts` 使用 `node:https.request`，把响应体当 Buffer 原样收下，由我们自己决定何时 `gunzip`。实现里用带 `keepAlive` 的 `https.Agent`（`maxSockets: 32`），避免每段都重新握手。

### 4.2 不要改成对「明文 5 MB」做 Range

如果请求 identity（不接受 gzip）再对 5 MB 明文分段，总传输会回到约 5 MB。在「整条链路聚合带宽有上限」的情况下，多连接只会把同一条窄路切得更碎，墙钟未必更好，还可能更差。本方法的目标是：**总字节仍约 1.9 MB，但用多条 TCP 把高时延单连接的等待叠起来**。

### 4.3 一致性、重试与回退

- 各段的 `ETag` 或 `x-goog-generation` 必须与探测时一致；中途对象更新则放弃本轮分段，改走整包。
- 单段失败最多再试 2 次（短暂退避）。
- 探测不是 206、压缩体太小、分段失败或长度对不上：回退为**单连接整包 gzip**，行为与旧方法相同，保证仍能拉下来。
- 清单文件同样走这一套（通常小于分段阈值，会自然走整包 gzip，仍然能享受压缩）。

### 4.4 并发参数（当前实现）

| 参数 | 值 | 含义 |
|---|---|---|
| `FILE_CONCURRENCY` | 3 | 同时下载几个文件 |
| `RANGE_PARTS` | 8 | 每个大文件拆几段 |
| `MIN_SIZE_FOR_RANGES` | 256 KB | 小于此大小的 gzip 体不分段 |
| 峰值连接 | 最多约 3 × 8 = 24，受 Agent `maxSockets: 32` 限制 | 生产机 2 核 4 G，按此配置已测过 |

入库（`ingestUploadFile`）仍在每个下载任务内完成。下载不再是「一条 TCP 卡满一个工人」时，这个顺序可以接受；不要为了微优化再改入库语义。

## 5. 验收数据（2026-11-10）

对照只跑下载与哈希，不写生产 API、不入库。目标文件：`STARLINK-38128.txt`、`STARLINK-37711.txt`、`STARLINK-38123.txt`。新旧方法解压后 SHA-256 前 16 位分别为 `d3e4860953aa0f7b`、`4a30313c942aa50d`、`5fc894038da29cee`，完全一致；每份明文约 5.02 MB，三份合计约 14.38 MB。

| 环境 | 旧：单连接 gzip × 3 文件 | 新：gzip 8 段 × 3 文件 | 墙钟倍率 |
|---|---|---|---|
| 生产服务器本机 | 140.9 秒（均 114.9 秒，最小 94.1，最大 140.9） | 25.1 秒（均 19.4 秒，最小 13.9，最大 25.0） | 5.62× |
| 开发笔记本 | 137.3 秒（均 100.9 秒，最小 79.1，最大 137.3） | 17.9 秒（均 12.6 秒，最小 9.3，最大 17.9） | 7.66× |

解读：

- 加速来自「同样约 1.9 MB 的 gzip 体，用 8 条并行 TCP 拉取」，不是改主机名，也不是改成明文分段。
- 北京到 GCS 的墙钟会波动（同日旧代码真实拉取曾是 76 秒 / 3 文件）。评估新代码应以**同一时刻、同一台机器上的新旧对照**为准；部署后的单次拉取允许在二十多秒上下起伏。
- 本机或国际出口较好的环境不能代替生产机测速。本次已在 `123.57.41.32` 本机跑过对照，不需要为了验证再先部署再测。

## 6. 实现时不要做的事

- 不要用 `fetch` / undici 去拉带 Range 的 gzip。
- 不要把 URL 改成 `*.txt.gz` 当作压缩方案。
- 不要为了「分段」而放弃 `Accept-Encoding: gzip`，改去切 5 MB 明文。
- 不要把 `starlink.com` 和 `api.starlink.com` 当成两个数量级不同的源；二者是同一对象。
- 不要在产品界面文案里写第三方商业 SSA 品牌；主机名只出现在服务端拉取实现里。
- 不要把本机 `data/ephemerides/` 缓存提交进 Git。
