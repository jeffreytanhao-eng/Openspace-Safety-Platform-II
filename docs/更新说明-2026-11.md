## 一、功能更新

### 1.1 星历数据链路

| 项目 | 说明 |
|------|------|
| NORAD 解析修正 | OCM 从 `OBJECT_DESIGNATOR` 字段读取真实目录号，ITC 从文件名 `MEME_<norad>_` 前缀读取；修正此前 STARLINK-1540→46051、1549→46074、37711→100002 等错误映射，全部与 TLE 编目库交叉验证 |
| 发布时间 | 元数据库新增 `published_at` 列并建索引；列表按发布时间倒序；星历卡片显示 UTC 紧凑格式（如 `11-01 04:54`），悬停查看秒级完整时间戳 |
| 同目标去重 | 同一 NORAD 的同格式（OCM/ITC）多份星历仅保留发布时间最新的一份（upsert 机制） |
| 原文件大小 | 元数据库记录 `raw_size`（解压后字节数），卡片与列表统一显示原大小而非 .gz 压缩大小 |
| 目录扫描导入 | 星历页「刷新」按钮触发服务端扫描 `data/ephemerides` 目录，新拷入未入库的星历自动导入，并反馈「新增 / 更新 / 跳过」计数 |

### 1.2 查看原文件

- 星历预览面板「文件」行右侧新增「查看原文件」按钮（服务端样本专属，本机导入记录不显示）
- 点击后新标签页打开原文件明文：后端 `/cgi/ephemerides/file` 接口自动 gunzip，以 `text/plain; charset=utf-8` 返回
- 说明：浏览器安全沙箱不允许网页调起系统默认应用（记事本等），新标签内直接显示原文本是 Web 端等效体验；如需下载原始 .gz，接口支持 `?download=1`

### 1.3 态势页星历分析面板重构

- **合并列表**：「内置星历样本」与「我的星历」合并为单一列表，按「名称+格式」去重（服务端优先），计数口径与星历管理页完全一致（当前 28 份 = 20 OCM + 8 ITC）
- **分页**：每页 6 张卡片，底部页码导航（‹ / 页码 / ›）
- **卡片 4 行布局**：第 1 行名称；第 2 行格式、机动数、协方差标签；第 3 行 NORAD + 有效期（UTC）；第 4 行点数 + 原文件大小
- **选中高亮**：当前激活星历卡片亮蓝边框 + 亮底显示，与未选中卡片明确区分
- **载入角标**：服务端样本卡片右上角「载入 / 重新载入」，点击即解析并激活，三维绘出完整轨道

### 1.4 三维交互

- **重复目标互斥**：星历激活的 NORAD 同步给编目云通道（`setEphemNorad`），全量卫星芯片/模型渲染时强制排除该目标——星历目标与编目云同时开启时大屏不会出现两个重复模型
- **低配自动降级**：沿用既有 LOD 机制（按全局可见数自动切换 low/med/high 模型档位），保证集显设备流畅

## 三、技术修复

| 问题 | 根因 | 修复 |
|------|------|------|
| 跳转态势后星历卡片偶发不高亮 | 星历面板挂载时的旧缓存清理循环调用 `removeEphem` 会清空当前激活态，清理到刚激活的旧错值记录导致高亮丢失（旧记录只删一次，故偶发） | 清理循环跳过当前激活记录；卡片高亮匹配改为按「名称+格式」（对旧缓存 NORAD 错值免疫） |
| 刷新 `/situation/eph?ephId=…` 深链偶发失效 | 深链慢路径按服务端列表定位目标行时默认只拉前 20 条，目标排在后面静默失效 | 显式拉全量列表 |
| 高倍速仿真轨道不连续 | SceneCore 仿真钟外部改动检测逻辑缺陷，导致每隔一帧回拉一次 | 陈旧推送值赋值移入条件分支内 |
| 全开关关闭后残留一条白轨道 | 编目选中态有 entryShown 恒真特判，目标失去全部可见通道后仍持续重画轨道 | `clearHiddenSelection`：失去全部可见通道且非空间站通道时清选中与准星 |
| 快速连点芯片目标卡在点云 | 构建请求竞态丢包 | 丢弃逻辑改为排队机制 |
| 芯片目标首次点亮闪点云 | glTF 资源网络下载延迟 | SceneCore 挂载后空闲静默预载全部 low LOD 几何 |
| 星历计数口径不一致（35 vs 28） | 本机 IndexedDB 旧解析缓存 NORAD 为旧错值，按 NORAD+格式无法与服务端样本去重 | 合并列表改按「名称+格式」去重（服务端优先） |

## 四、部署体系

### 4.1 线上环境

- **服务器**：阿里云 123.57.41.32（Ubuntu 24.04，2核4G）
- **组件**：Nginx 80（gzip_static，`/cgi` → 127.0.0.1:1234）+ systemd `openspace-api`（node dist/server.js）+ MySQL 8.0.46（库 openspace）
- **数据量**：sat_tle_history 216 万行、sat_conjunction 166 万、sat_cri_conj 170 万、星历元数据 28 条
- **资源水位**：内存已用 1.1G/3.4G、CPU load ≈ 0、磁盘 7.8G/49G；无 Swap（数据量增长后建议评估）

### 4.2 部署流程（已固化）

```
本地：web npm run build → tar 打包（api 源码不含 node_modules + dist + data/ephemerides）
上传：paramiko SFTP（必须确认 100% 传完再触发下一步）
服务器：tar 解压 → npm ci → npm run build → systemctl restart openspace-api
```

### 4.3 运维经验

- tar 为**叠加解压**：数据文件重组/删除后需同步清理服务器残留文件，否则旧数据混入（本次曾导致星历计数 44 ≠ 28）
- 公网验证口径：首页 200 + `/cgi/health` 返回 `db: up` + 星历分页接口 `source:"db"` + 前端 bundle hash 与本地构建一致
- Windows→Linux 自动化：paramiko exec 长命令需服务器端 nohup 后台跑 + 轮询日志
